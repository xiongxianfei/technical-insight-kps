# Instructions for assisted authoring

## Key takeaway

Assistants must make evidence assumptions and execution status explicit.

## Summary

This file summarizes authoring and publication instructions for people and automated assistants working on this domain. The linked KPS Core contract remains authoritative. These instructions do not constitute a Principle or a scientific claim.

## Content responsibilities

Use the five core types. Technical insight is a domain and a kind of synthesis, not a sixth type. A Principle explains a reusable relationship without prescribing a specific design. A source record preserves the source’s contribution rather than our preferred conclusion.

Every significant Markdown file needs a meaningful takeaway, summary, local explanation/procedure and limits. Practice stages use StageN headings, recommended order, inline procedures, observations and fallbacks. Never replace essential safety or rationale with a link.

## Evidence responsibilities

Inspect sources for claims that need support. Preserve source identity, locators, access extent, family/independence and disagreement. Mark own inferences and synthetic examples. Do not invent experiments, measured outcomes, permissions, checks or source access.

## Publication responsibilities

Read the current corresponding repository before making changes. Open ready-for-review PRs when authorized; never merge or create official releases without separate approval. When no repository exists, prepare a validated ZIP. Do not repurpose a similarly named but unrelated repository.

Preserve the shared manifest-payload exclusions in the validator and its tests. Do not disable integrity checks to get green CI. Update summary hashes only after review and report exactly which checks ran.
